**Goal:** Let a carrier move shipments: `POST /api/v1/webhooks/carrier` accepts HMAC-signed status events,
verifies each one over the raw request bytes and feeds it through the M3 event pipeline (state machine,
idempotent duplicates, `occurredAt` guards) with `source: WEBHOOK`; a rate limit protects the route; and
`npm run simulate -w apps/api` fires realistic signed event sequences at the API — so M6's timeline shows
carrier-driven movement and M7 can demo it live.

**Architecture:** `packages/shared` owns the HTTP contract of the webhook (payload schema, acknowledgement
schema, signature header name, the `INVALID_SIGNATURE` code). In `apps/api`, `lib/hmac.ts` signs and verifies
(`node:crypto`, constant-time). `lib/carriers/` holds the pluggable-carrier seam from spec §9: the
`CarrierAdapter` interface and its one MVP implementation, `SimulatedCarrierAdapter`, whose `parseWebhook`
verifies the signature, parses the JSON and returns a normalized `CarrierEvent`. `modules/webhooks/` is a
route plus a thin service: the route plugin reads the body as raw bytes through a content-type parser scoped
to that plugin (every other route keeps Fastify's JSON parsing), the service finds the shipment by tracking
number and carrier and calls M3's `appendShipmentEvent` — still the only code path that writes a
`MovementEvent`, and **not modified by M4**. The simulator lives in `apps/api/scripts/`: a core (scenarios,
signing, runner with an injected sender — tested in Vitest against the real app through `app.inject`), a CLI
layer (argv, output, exit code) and a three-line entry file.

**Tech Stack:** Fastify 5.10 (encapsulated content-type parser, per-route `bodyLimit`), `@fastify/rate-limit`
11.2 (already registered with `global: false` in M2), `node:crypto` (`createHmac`, `timingSafeEqual`),
`node:util` `parseArgs` and the global `fetch` for the CLI, `tsx` 4.23 to run it, Zod 4.6, Prisma 7.9 +
`@prisma/adapter-pg`, Vitest 4.1 with `fastify.inject()` against docker Postgres 16, TypeScript 6.0.3,
Node 20. **No new dependencies and no new migration** — M4 uses exactly what M0–M3 installed.

**Spec:** `shipment-tracker-spec.md` — §7 (API Design → Webhooks, Security requirements, Shipment decisions →
Manual events and Idempotency), §9 (Carrier Integration Design), §10 (Testing), §12 (Execution; §12.7 names
M4 as an extra-weight checkpoint). Task 1 writes the decisions below into the spec, so after Task 1 the spec
and this plan agree.

## Decisions (M4 human checkpoint, 2026-11-12)

Decided by the project owner:

| # | Question | Decision |
|---|---|---|
| D1 | How the route gets the raw body | A content-type parser for `application/json` with `parseAs: 'buffer'`, registered inside the webhook plugin only. The handler receives a `Buffer`; order is signature → `JSON.parse` → Zod. No `fastify-raw-body`, no `preParsing` hook. |
| D2 | Invalid signature | `401` with a new code `INVALID_SIGNATURE`, message `Invalid webhook signature`. One identical body whether the header is missing, malformed or does not match. |
| D3 | Replay protection | None in the MVP — the signature covers the body only, as in the spec. A replayed request is an exact duplicate and therefore a `200` no-op. A signed timestamp is roadmap. |
| D4 | `WEBHOOK_SECRET` | Required, at least 32 characters (the `JWT_SECRET` rule). The API refuses to start otherwise. |
| D5 | `occurredAt` in the future | Same strict guard as manual events: `400 VALIDATION_ERROR` on `occurredAt`, no clock-skew tolerance. `appendShipmentEvent` is unchanged. |
| D6 | Event older than the shipment's latest event | Rejected exactly as in M3: `400 VALIDATION_ERROR` on `occurredAt`, nothing stored. No new code, no pipeline change. |
| D7 | Unknown `trackingNumber` | `404 NOT_FOUND`, message `Shipment not found` — the body `GET /shipments/:id` already uses. No new code. |
| D8 | Success response | `201` for a stored event, `200` for an exact duplicate; body `{ trackingNumber, shipmentStatus, duplicate }`. The carrier never receives the client's name or email or the timeline. |
| D9 | Payload | The spec's four fields plus an optional `note` (≤ 500 characters). `occurredAt` is required. |
| D10 | `Shipment.carrier` | The shipment is looked up by `trackingNumber` **and** `carrier` = the adapter's name (`SIMULATED`); another carrier's shipment is the same `404`. |
| D11 | Pluggable adapter (spec §9) in M4 | The `CarrierAdapter` interface and one implementation, `SimulatedCarrierAdapter`, wired directly to the single route. No registry, no `/webhooks/:carrier`, no `fetchStatus`, poller or status mapping tables. |
| D12 | Rate limit | 120 requests per minute per IP on `POST /webhooks/carrier`; its own counter; every request counts, valid or not; applied before the body is read ⇒ `429 RATE_LIMITED` with `Retry-After`. |
| D13 | Where the simulator lives | `apps/api/scripts/simulate-carrier.ts`, run with `npm run simulate -w apps/api -- <trackingNumber> [flags]`. |
| D14 | Simulator CLI | Named scenarios — `delivery` (default), `direct`, `exception`, `recovery`, `duplicate`, `illegal`, `bad-signature`. Each scenario knows the status codes it expects; exit code `0` only when the API answered exactly that. `--delay` (default 1000 ms), `--url`. |
| D15 | How the simulator is verified | Vitest for the core (all scenarios through `app.inject` against the real app and test database) plus a smoke test of the CLI against a running API in Task 11. |

Consequences of these decisions the owner accepted:

- **D6** A late event — older than the shipment's latest stored event and not an exact duplicate — is lost for
  good: the carrier's retries keep getting `400`. Reconciliation of out-of-order events is roadmap. (An
  out-of-order delivery whose transition is *illegal* gets `422` and succeeds on a later retry, once the
  missing event has arrived.)
- **D5** A sender whose clock is ahead of the server gets `400`. The simulator run from a laptop against a
  deployed API therefore depends on the laptop's clock.
- **D5 + D6** The simulator cannot paint a multi-day history: every event it sends lies between the
  shipment's creation and now, stamped with the send time. Demo history stays in `prisma/seed.ts`.
- **D3** A replay is a no-op only for events that were stored. A captured request that was *rejected* at the
  time can be accepted later if the shipment's state has changed so that it became legal — the same thing a
  carrier's own retry does.
- **D12** Until Fastify `trustProxy` is wired in M7 (spec §11), all webhook senders behind the hosting proxy
  share one rate-limit bucket.

Implementation calls shown to the owner with the contract summary and approved with it:

- **C1** The route's body limit is 16 KiB (a valid payload is under 4 KiB); a larger body ⇒ `413`.
- **C2** Hex digits of the signature are accepted in either case; the `sha256=` prefix only in lower case.
- **C3** `location: null` / `note: null` ⇒ `400`, as for manual events (optional, not nullable).
- **C4** `source` stays `WEBHOOK` — the value is already in the shared contract, the schema default and the
  seed. No new source value, no per-event carrier column, no migration.
- **C5** The shared text helpers `cleanText` / `optionalCleanText` move to an internal module of
  `packages/shared` so the webhook payload reuses the manual-event rules instead of copying them; the payload
  schema is `createShipmentEventSchema` extended with `trackingNumber` and a required `occurredAt`.
- **C6** All 49 status pairs are exercised through the webhook as well (same helper as M3).
- **C7** The simulator neither creates shipments nor retries a `429`.

Implementation calls made while planning (flagged for the reviewer, not owner decisions):

- **C8** Fastify answers a wrong content type (`415`) and an oversized body (`413`) before the handler runs,
  so these two precede the signature check; both use the code `BAD_REQUEST`. A request with no body and no
  content type reaches the handler with `request.body === undefined` and is treated as zero bytes.
- **C9** `INVALID_SIGNATURE` sits after `INVALID_CREDENTIALS` in `ERROR_CODES` (the list is ordered by status).
- **C10** `SimulatedCarrierAdapter` is a class holding the secret in a `#private` field (invisible to
  `JSON.stringify` and `util.inspect`). `parseWebhook` reports failures by throwing `AppError` / `ZodError`,
  which the existing error handler already maps.
- **C11** Tests never sign with `src/lib/hmac.ts`: the test helper `signBody` computes the HMAC with
  `node:crypto` directly, so the production signer is checked against an independent oracle (plus the RFC 4231
  vector in Task 4 and `openssl` in Task 11).
- **C12** Task 7 adds no production code — the pipeline is M3's. Its tests are green on the first run by
  design; two temporary mutations prove they bite.
- **C13** `trackingNumber` is trimmed and then matched exactly (case-sensitive); its format is not validated.
- **C14** `webhookRateLimit` is a constant in `config.ts`, not env-driven (like `authRateLimit`).
- **C15** The simulator is three files: core, CLI layer returning an exit code (`0` as expected, `1` mismatch
  or network failure, `2` usage or missing secret), and an entry file. The CLI layer takes `fetch` and the
  output functions as parameters, so Vitest drives it end to end without a network.
- **C16** Scenario locations describe one fixed route (Kyiv → Lviv); the simulator has no read access to the
  shipment, so it cannot know its real origin and destination.
- **C17** No extra log lines for rejected webhooks; Fastify's request log already records the `401`.

Not in M4 on purpose: a signed timestamp / replay window, clock-skew tolerance, out-of-order reconciliation,
an adapter registry and `/webhooks/:carrier`, `fetchStatus` and the poller, per-carrier status mapping tables,
secret rotation, `trustProxy` (M7), a README section (M7), any frontend work (M5–M6).

- "`VALIDATION_ERROR` on `x`" means: status `400`, `error.code === 'VALIDATION_ERROR'`,

- `FUTURE` = `[{ path: 'occurredAt', message: 'occurredAt must not be in the future' }]`,
  `EARLIER` = `[{ path: 'occurredAt', message: 'occurredAt must not be earlier than the latest event' }]`.

## Review Focus

Inputs the spec implies but does not spell out; each is pinned by a test in the task named in brackets.

1. The signature covers bytes, not meaning: the same JSON re-serialized with different whitespace under the
   old signature is a `401`; any formatting is accepted when it is signed as sent. [Tasks 4, 6]
2. The raw-body parser must not leak: auth and shipment routes still receive parsed JSON, a `text/plain` body
   still reaches them, and their malformed-JSON answer is unchanged. [Task 6]
3. Unauthenticated garbage never produces a `500` or a body outside the envelope: no body, an empty body,
   non-JSON, JSON that is not an object, a wrong content type, an oversized body, a NUL character, a repeated
   signature header. [Tasks 5, 6, 7]
4. Carrier retries behave: a redelivery after the shipment has moved on is `200`, not `422`; a redelivery
   with different bytes (key order) is still a duplicate; parallel redeliveries store one event; an event
   already recorded by a dispatcher is a duplicate too. [Task 7]
5. A rejected webhook leaves no trace — no `MovementEvent`, `status` and `updatedAt` unchanged — for `401`,
   `400`, `404`, `422` and `429`. [Tasks 6, 7, 8]
6. The secret stays secret: not in a `401` body, not in a config error, not in `JSON.stringify(adapter)`, not
   in simulator output. [Tasks 3, 5, 10]

    - `signPayload(payload: string | Buffer, secret: string): string` — `SIGNATURE_PREFIX` + the lowercase hex
      HMAC-SHA256 of `payload` keyed with `secret` (a string is hashed as UTF-8). This is the value of
      `X-Carrier-Signature`; the simulator (Task 9) signs with it.
    - `verifySignature(payload: string | Buffer, signature: unknown, secret: string): boolean` — `true` only

      `payload`. Never throws, whatever `signature` is.
  - From `apps/api/tests/helpers/webhooks.ts` (the test oracle, C11):
    - `signBody(body: string | Buffer, secret: string): string` — the same value computed with
      `createHmac('sha256', secret).update(body).digest('hex')` directly. It must **not** import
      `src/lib/hmac.ts`.

`verifySignature`, in this order: not a string → `false`; no match for `/^sha256=([0-9a-fA-F]{64})$/` →
`false`; otherwise compare the 32-byte digest decoded from the hex with the 32-byte digest computed from
`payload` using `timingSafeEqual`. The format check comes first because `timingSafeEqual` throws on buffers of
different length and `Buffer.from(text, 'hex')` silently drops invalid characters.

The module is pure: no Fastify, no config, no `AppError`.

`webhookRoutes` — the plugin function receives its own encapsulated instance; everything below is called on
that instance, never on the root app:

1. `const adapter: CarrierAdapter = new SimulatedCarrierAdapter(app.config.webhookSecret);`
2. `app.removeAllContentTypeParsers();` then
   `app.addContentTypeParser('application/json', { parseAs: 'buffer' }, (_request, body, done) => done(null, body));`

Signature and transport:

- The HMAC is computed over the raw request bytes; the same JSON with different whitespace under an old
  signature is a `401` (Tasks 4, 6). `openssl` produces a signature the API accepts (Step 2, line 15).

- A missing, malformed, repeated or non-matching signature gives one byte-identical `401 INVALID_SIGNATURE`;
  the signature is checked before the body is parsed and before the shipment is looked up, so an unsigned
  caller learns nothing about which tracking numbers exist.
- The raw-body parser exists only in the webhook plugin; auth and shipment routes parse JSON as before
  (Task 6 isolation rows, full M2 + M3 suites green).
- `WEBHOOK_SECRET` is required and at least 32 characters; the API refuses to start otherwise (Task 3,

- One write path: the webhook goes through `appendShipmentEvent` with `source: WEBHOOK`; the `git diff` in
  Step 1 shows M3's pipeline and tests untouched.
- All 49 status pairs through the webhook: 20 accepted, 29 answered `422` with the snapshot unchanged.
- Idempotency: an exact duplicate is a `200` no-op — after the shipment moved on, with other bytes, in
  parallel, and across sources (an event a dispatcher already recorded).
- `occurredAt` guards apply to webhooks exactly as to manual events (future ⇒ `400`, older than the latest

- Carrier scope: only `carrier = 'SIMULATED'` shipments; another carrier's shipment is the same `404` as an
