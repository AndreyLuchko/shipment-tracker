**Goal:** Give the API a complete session layer — `POST /api/v1/auth/register`, `POST /api/v1/auth/login`,
`POST /api/v1/auth/logout`, `GET /api/v1/auth/me` — with a JWT in an HttpOnly cookie, session-bound CSRF
protection, a single error envelope, rate-limited credential endpoints, and the HTTP contract published from
`packages/shared`, so M3 can protect shipment routes with `app.authenticate` / `app.requireRole`.

**Architecture:** `packages/shared` owns the HTTP contract (Zod schemas for auth requests/responses, the error
envelope, cookie/header names). In `apps/api`, four `fastify-plugin` plugins carry the cross-cutting concerns:
`errorHandlerPlugin` (every failure → `{ error: { code, message, details? } }`), `csrfPlugin`
(`app.verifyCsrf`), `authPlugin` (`@fastify/cookie` + `@fastify/jwt`, `app.authenticate`, `app.requireRole`),
plus the existing `prismaPlugin`. `app.authenticate` verifies the JWT from the `access_token` cookie and, for
unsafe HTTP methods, also requires `X-CSRF-Token` header = `csrf_token` cookie = `csrf` claim inside the JWT —
so any route that uses the session is CSRF-protected automatically and public routes need no opt-out flag.
The auth module (`modules/auth/`) is routes → service → Prisma; password hashing reuses
`hashPassword`/`verifyPassword` from `apps/api/src/lib/password.ts` unchanged.

**Tech Stack:** Fastify 5.10, `@fastify/cookie` 11, `@fastify/jwt` 10 (HS256), `@fastify/rate-limit` 11,
Zod 4, Prisma 7 + `@prisma/adapter-pg`, Vitest 4 with `fastify.inject()` against docker Postgres 16,
TypeScript 6.0.3. (Majors verified against the npm registry on 2026-11-11.)

**Spec:** `shipment-tracker-spec.md` — §7 (Auth table + Security requirements), §10 (Testing), §12
(Execution). Task 1 writes the decisions below into §7, so after Task 1 the spec and this plan agree.

## Decisions (M2 human checkpoint, 2026-11-11)

Decided by the project owner:

| # | Question | Decision |
|---|---|---|
| D1 | How the browser reaches the API | Same-origin through Next.js rewrites (`/api/v1/*` → API), built in M5/M7. M2 registers **no CORS plugin**; cookies are host-only (no `Domain`), `Path=/`. |
| D2 | JWT lifetime / refresh | One HS256 JWT, 24 h, cookie `Max-Age` = 86400. No refresh token, no session table. Logout only clears cookies. |
| D3 | CSRF token | 32 random bytes generated on login/register; stored in the `csrf_token` cookie **and** as the `csrf` claim of the JWT. Rotated only when a new session starts. |
| D4 | `Secure` without local HTTPS | Always `Secure`; only an explicit `COOKIE_SECURE=false` disables it. |
| D5 | Error format | `{ error: { code, message, details? } }`; `details: [{ path, message }]` only on `VALIDATION_ERROR`. `AppError` + centralized `errorHandlerPlugin`. |
| D6 | Rate limit | `POST /auth/login` and `POST /auth/register`: 5 requests / minute / IP each. `me` and `logout` unlimited. |
| D7 | Zod in `packages/shared` | The whole HTTP contract: request schemas, public user, error envelope + codes, CSRF cookie/header names. |
| D8 | Register | Starts a session immediately (same cookies as login), `201`. |
| D9 | Test database | Separate `shipment_tracker_test` database in the same docker Postgres; truncated between tests; test files run sequentially. |
| D10 | TypeScript version | All workspaces on `^6.0.3` (`typescript-eslint` 8.x supports only `<6.1.0`; the API already typechecks clean under 6.0.3). |

Implementation calls made while planning (flagged for the reviewer, not owner decisions):

- **C1** Validation is `schema.parse(request.body)` in the handler; the thrown `ZodError` is mapped by the
  error handler. No `fastify-type-provider-zod` (it requires `@fastify/swagger` as a non-optional peer).
- **C2** Session verification is stateless: `sub` + `role` come from the token. Only `/auth/me` reads the DB.
- **C3** CSRF verification lives inside `app.authenticate` (unsafe methods only) rather than in a global hook
  with opt-out flags: same "cannot forget to protect a route" guarantee, no flags, no hook-ordering pitfalls.
- **C4** `app.requireRole(role)` ships in M2 (tested on a throwaway route) so M3 does not reopen the auth plugin.
- **C5** Login returns the identical `401 INVALID_CREDENTIALS` for unknown email and wrong password, and runs
  a dummy scrypt verification when the user does not exist. Duplicate email on register → `409 EMAIL_TAKEN`.
- **C6** Email is trimmed + lowercased before validation; password is 8–128 characters and never trimmed.

Deferred, recorded in the spec by Task 1: Next.js rewrites (M5), Fastify `trustProxy` so `request.ip` is the
real client behind the proxy (M7), refresh tokens / revocation (roadmap).

- [ ] **Step 3: §7 — insert this block directly after the "Security requirements" list**

```markdown
**Auth decisions (M2 human checkpoint, 2026-11-11):**
- **Session:** one HS256 JWT in `access_token`, lifetime 24 h, cookie `Max-Age` equal to the token lifetime.
  No refresh token and no session table. Claims: `sub` (user id), `role`, `csrf`. Verification is stateless;
  logout only clears the cookies, so an already-issued token stays valid until it expires (accepted MVP
  limitation — refresh tokens and revocation are roadmap).
- **CSRF token:** 32 random bytes generated server-side on login and register, stored both in the
  `csrf_token` cookie and as the `csrf` claim of the JWT. Every unsafe method (POST/PUT/PATCH/DELETE) on an
  authenticated route requires `X-CSRF-Token` header = `csrf_token` cookie = `csrf` claim, otherwise `403
  CSRF_TOKEN_INVALID`. The token rotates only when a new session starts. Public routes (login, register,
  webhook) are not CSRF-checked — they do not act on a session.
- **Cookies:** `Secure` is always on; only an explicit `COOKIE_SECURE=false` in a local `.env` turns it off
  (for browsers that reject `Secure` cookies over `http://localhost`). Host-only (no `Domain`), `Path=/`.
- **Topology:** the browser reaches the API same-origin through Next.js rewrites (`/api/v1/*` → API).
  This is required, not optional: `SameSite=Lax` cookies are not sent on cross-site `fetch`, and JS cannot
  read a cookie set by another site, and Vercel and Render hostnames are different sites. The API therefore
  registers no CORS plugin.
- **Rate limits:** `POST /auth/login` and `POST /auth/register` — 5 requests per minute per IP each ⇒ `429
  RATE_LIMITED` with `Retry-After`. `/auth/me` and `/auth/logout` are not limited.
- **Credentials:** email is trimmed and lowercased; password is 8–128 characters and never trimmed. Login
  answers `401 INVALID_CREDENTIALS` identically for an unknown email and a wrong password. A taken email on
  register ⇒ `409 EMAIL_TAKEN`.
- **Error codes (M2):** `VALIDATION_ERROR`, `BAD_REQUEST`, `UNAUTHORIZED`, `INVALID_CREDENTIALS`,
  `FORBIDDEN`, `CSRF_TOKEN_INVALID`, `NOT_FOUND`, `EMAIL_TAKEN`, `RATE_LIMITED`, `INTERNAL_ERROR`. The list
  lives in `packages/shared` and grows with later milestones.
```

  - `RegisterInput` and `LoginInput` are the **parsed output** types (`z.infer`).

Field rules: email — trim, lowercase, then validate as an email, max 254. Register password — 8 to 128
characters, not trimmed. Login password — 1 to 128, not trimmed. Name — trimmed, 1 to 100. Role — optional
in the input, defaults to `'CLIENT'`. Unknown keys are stripped (plain object schemas, not strict).
